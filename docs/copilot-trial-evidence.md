# Copilot trial evidence and credit-usage assessment (issue #194)

This document is the evidence record `docs/automation.md` § [Copilot trial evidence and credit-usage assessment](automation.md#copilot-trial-evidence-and-credit-usage-assessment-issue-194) links to. It inventories real Copilot pull requests and runs against the original integration requirements, records a small trial of bounded tasks reusing completed work, states what usage data is and is not available, and reconciles Nayax documentation access with issue #192. It does not change any workflow, model-tier mapping, or routing behaviour; it is read-only evidence and assessment.

**Method and limits.** Every fact below was read from the public GitHub issue/PR/comment/review history with `gh issue view`, `gh pr view` and the issue/PR comment and review bodies the agent workflows post. This session's tool permissions do not include `gh run list`, `gh pr checks`, `gh api`, or `gh label list` (they require interactive approval that is not available to an unattended agent run), so individual Actions run logs, raw check-run results, and the live repository label list could not be read directly. Where a fact depends on one of those, it is marked **unavailable** rather than inferred. Run URLs quoted from issue comments are reproduced as evidence of what the workflow itself reported, not independently re-verified by opening the run.

Whether a human has completed that one-time step cannot be confirmed or denied here. None of the seven Copilot PRs inventoried in § 1 touched a new Nayax request/response contract (they migrate existing fee/commission/costing logic and an Angular view split), so none of them required a Nayax documentation lookup, and their absence of a "Nayax documentation unavailable" disclaimer is not evidence either way for the coding agent's MCP setting.

A human should confirm that setting directly in repository Settings; this task does not and cannot configure it (that would be a `.github/**`-equivalent repository-setting change outside this issue's authorization).

## 4. Usage-measurement limitations

Per the issue's explicit instruction, unavailable usage is recorded as **unavailable**, not estimated from turn counts, commit counts, or elapsed time:

- Neither the Copilot coding agent nor the Copilot CLI (architecture check, final review) exposes per-run token, request, or premium-request consumption anywhere this session can read: not in the issue/PR text, not in the workflow's own comments, and not in a file in this repository. `docs/automation.md` § Credentials used by the agent workflows documents that `COPILOT_AGENT_TOKEN` and `COPILOT_CLI_TOKEN` are scoped credentials, not telemetry sources.
- Claude invocations (implementation, architecture check/fix, review, triage, repair) similarly report no usage figure into the repository. `CLAUDE_CODE_OAUTH_TOKEN` is a billing credential, not a readable meter, from this vantage point.
- Actual consumption, if it is visible at all, would be on each provider's own billing/usage dashboard (Anthropic Console for Claude, GitHub's Copilot premium-request usage page for Copilot), which is outside this repository and outside this agent's tool access. This task does not have access to either dashboard and does not estimate a number in their place.
- The one quantity this session **can** read per task is the implementation model/tier the triage step selected (recorded per task in § 3.2) and, separately, elapsed wall-clock time. Neither is a credit-usage figure, and `docs/automation.md` § Implementation model tiers is explicit that the tiers govern implementation selection only, not total workflow cost — architecture checks, fixes, reviews, triage and repairs keep their existing models regardless of the chosen implementation tier.
- Consequently: **this assessment cannot state a credit or cost comparison between Claude and Copilot**, in aggregate or per task. Any such comparison would have to come from a human reading both providers' billing dashboards for the exact date ranges in § 3.2, which is outside this read-only task's authority and tooling.

## 5. Gaps that keep this trial incomplete

Per the issue's instruction not to fabricate results or close solely because workflows exist, the following are explicitly recorded as gaps rather than papered over:

- **No credit/usage figures** for any task, provider, or stage (§ 4). This is the single largest gap relative to the issue's request.
- **No full-provider fallback evidence exists yet, and none can exist yet.** Issue #337's four pull requests (#342, #344, #349, #350 — label parsing/exclusivity, provider-mode provenance, routing/enabling the fallbacks, and the rollout audit) are merged into `develop` (confirmed: commit `874efde` is an ancestor of `origin/develop`) but **not yet released to `main`** (confirmed: the same commit is **not** an ancestor of `origin/main`). Because `issues`/`issue_comment`-triggered agent workflows run only from `main` (`docs/automation.md` § Provider roles and readiness labels), `agent-ready-full-claude` and `agent-ready-full-copilot` are not yet routable in this repository regardless of `FULL_PROVIDER_EXECUTION_ENABLED`'s value in the `develop` copy of `scripts/agent-mode.mjs`, and regardless of whether the two labels have been created in repository settings (which this session also cannot read; see § Method and limits). No same-provider review trial data can be collected until a human releases that work to `main`.
- **Three candidate trial tasks are in flight, not completed**, and are therefore excluded from § 3's scored sample rather than reported with invented outcomes: issue #362 ("Keep the sales sync saving other products' costs when one product's cost history fails"), #165 ("Add Azure Monitor OpenTelemetry error observability", `risk:high`), and #68 ("Define Azure Functions hybrid workload criteria", `risk:low`) are all currently labelled `agent-working` as of this writing. This issue does not authorize starting, labelling, or otherwise advancing them; their eventual outcomes should extend this evidence document once they complete, under a separate human-authorized follow-up.
- **The Copilot coding agent's MCP server setting for Nayax documentation access is unverified** (§ 2), as is whether any Copilot or Claude invocation in the inventoried PRs actually exercised a Nayax documentation lookup rather than merely having one available.
- **Raw Actions run logs, check-run results, and the live repository label list could not be read in this session** (§ Method and limits), so some claims above (exact-SHA validation success inferred from a published verdict; the precise wording of triage comments) rest on the workflow's own public comments rather than a second, independent confirmation from the run log itself.

## 6. Factual assessment and recommendation

Based only on the evidence above:

- The Copilot integration's **configured** capabilities in `docs/automation.md` (assignment, architecture check, SonarCloud fold-in, exact-SHA validation gating, independent Claude review, bounded fix cycles, failure/blocked recovery, model-tier selection) are **observed executing**, not merely present in workflow files, across the five scored tasks and the two supporting ones in § 1. The one component not yet observable — full-provider fallback — is not observable because its implementation has not reached `main` yet (§ 5), which is a release-sequencing fact, not a defect in the fallback implementation itself.
- Within the scored sample, Copilot completed 4 of 5 tasks without a human-visible content defect reaching final review (clean or SonarCloud-only findings), and the fifth (#150) recovered correctly from both an agent-side failure and a real review rejection through the documented blocked-recovery and fix-and-re-review paths, without any guardrail being bypassed or weakened. This is evidence the safety mechanisms around Copilot (independent architecture check and review, bounded fix cycles, fail-closed blocking) work as designed when exercised, not evidence about Copilot's general reliability or speed, which a sample of five naturally-occurring tasks cannot establish statistically.
- **No cost or credit comparison between Claude and Copilot can be made** from available evidence (§ 4). Any recommendation on provider choice that turns on cost must wait for a human to read both providers' own usage dashboards; this document does not substitute an estimate.
- Per the issue's explicit exclusion, **this assessment does not propose, and nothing here should be read as justifying, an automatic "best agent" selection or provider-routing algorithm.** Provider choice should remain the explicit human decision `docs/automation.md` already requires, informed by whichever qualitative evidence in § 1–§ 3 is relevant to the next task, not by an automated score derived from this sample.
- **Recommended next steps for a human**, none of which this issue authorizes this agent to perform: (1) confirm the Copilot coding agent's Nayax MCP setting in repository Settings; (2) decide whether and when to release #337's four merged pull requests to `main` so the full-provider fallback becomes routable and observable; (3) if a larger or more current trial is wanted, authorize specific additional tasks (for example once #362, #165 or #68 complete) rather than treating this document as final; (4) if a credit/cost comparison is wanted, pull the relevant date-ranged figures from each provider's own billing dashboard, since this task's tooling cannot.

This trial is **incomplete** by design, consistent with the issue's instruction to keep it incomplete rather than fabricate a conclusion the evidence does not support.
